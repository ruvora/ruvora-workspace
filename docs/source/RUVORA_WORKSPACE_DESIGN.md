# RUVORA Workspace 제품 기획 v0.2

작성일: 2026-09-06. 이름 확정, 나머지는 구현 전 제품 제안이다. 이번 문서는 실제 기능 출시나 설치를 뜻하지 않는다.

## 1. 한 문장 정의

**RUVORA Workspace는 프로젝트의 맥락을 찾고, 일을 이어서 실행하고, 완료된 기록을 정리하고, 검증된 세션을 다른 환경으로 가져갈 수 있게 하는 로컬 작업 공간이다.**

현재 실행 엔진은 Codex를 대상으로 한다. Codex의 편집기·채팅·Git UI를 대체하지 않는다. 사용자는 여전히 대화에서 요청하고 실제 작업 스레드에서 결과를 확인한다. Workspace는 그 사이에 흩어진 맥락과 진행 상황, 다음 행동을 연결한다.

Hub·Graph·Fold·Port 이름을 알아야 쓸 수 있는 제품이 되지 않도록 사용자 메뉴는 현황, 맥락, 작업, 정리, 이전으로 표현한다. 상세 설정·진단에는 실제 담당 제품을 표시한다.

## 2. 우선 사용자와 해결할 문제

1차 사용자는 같은 프로젝트에서 여러 날 Codex 작업을 이어가며 스레드가 누적되는 개인 개발자다. 여러 프로젝트를 번갈아 관리하는 개발자가 2차 사용자다. 팀 계정·공동 실시간 편집·조직 관리자 기능은 초기 범위에 넣지 않는다.

| 상황 | 지금의 부담 | Workspace가 제공할 가치 |
| --- | --- | --- |
| 며칠 뒤 프로젝트 복귀 | 무엇을 결정했고 어디서 멈췄는지 찾음 | 출처와 시점이 있는 현재 맥락·진행·미해결 사항 |
| 후속 작업 시작 | 비슷한 여러 스레드 중 선택 | 추천 이유·범위·차이를 보고 기존 맥락으로 시작 |
| 복잡한 작업 관찰 | 내부 보조 스레드를 일일이 열음 | 대표 작업 링크와 실제 진행·대기 원인 |
| 완료 후 목록 정리 | 증거를 지울까 봐 방치 | 통합안 검토 후 보조 기록 아카이브·복원 |
| 다른 환경에서 이어가기 | 요약으로 중요한 맥락이 사라짐 | 검증된 범위의 독립 패키지 이전. Port 출시 관문 충족 후 제공 |

핵심 성공 경험은 “이 프로젝트를 다시 열어, 어떤 맥락으로 다음 작업을 시작할지 빠르게 판단했다”이다. 스레드 수 감소만으로 제품 성공을 판단하지 않는다.

## 3. Workspace의 단위와 정보 모델

기본 단위는 호스트가 선택한 하나의 프로젝트다. 첫 버전에서는 여러 레포를 새 논리 프로젝트로 합치지 않는다. Hub의 기존 다중 프로젝트 기능을 호출할 때는 별도로 모든 대상 범위를 보여준다.

| 객체 | Workspace가 보관할 것 | 소유하지 않는 것 |
| --- | --- | --- |
| WorkspaceProfile | local ID, host/project 참조, 표시 이름, 사용자 환경설정 | 원본 프로젝트 디렉터리·Git 상태 |
| ContextSelection | Graph/Fold/원본 참조와 선택 이유·revision | 복제된 전체 대화 저장소 |
| WorkCard | Hub run ID, 대표 thread 참조, 관찰 시점 | Task 상태·완료 판정 |
| WorkflowTicket | 사용자 요청, 승인된 단계, 제품 operation ID, 다음 행동 | 별도 작업 DAG·스케줄러 |
| ReviewCard | Fold/Port 계획 참조, 영향·승인 상태 | 재사용 가능한 전역 승인 |

`hostId + canonicalProjectId`를 프로젝트 정체성으로 사용하고 절대 경로는 별도로 검증한다. 이름이 같거나 디렉터리가 이동했다고 다른 프로젝트의 기록을 자동 합치지 않는다. 프로젝트 이전·재연결은 사용자 확인이 필요하다.

## 4. 진입점과 화면

기본 진입점은 자연어 요청이다. “Workspace 열어줘”라고 하면 프로젝트 현황을 표시한다. 작업마다 전체 대시보드를 자동으로 띄우지 않는다. Hub 작업의 대표 링크·진행 패널은 Hub의 현재 경험을 재사용한다.

첫 UI는 호스트 내 읽기 중심 패널을 목표로 한다. 호스트에서 지원되지 않으면 동일 데이터의 대화형 보고서를 제공하며, 임베디드 화면 가능 여부와 클릭 검증을 출시 조건으로 둔다. 별도 웹사이트나 상시 공개 서버는 만들지 않는다.

### 현황 화면

위에서 아래로 다음을 표시한다.

1. **프로젝트·연결 상태:** 현재 범위, 마지막 확인 시점, 서비스 연결 문제
2. **주의가 필요한 일:** 승인 대기·실패·복구·미통합 결과물. 실제로 확인된 항목만 표시
3. **이어갈 작업:** 실행 중 또는 최근 대표 작업, 목적, 진행, 결과/작업 열기
4. **현재 맥락:** 선택된 결정·제약·미해결 사항, 원본 출처, 오래된 정보 표시
5. **정리와 이전:** 저장된 미리보기·처리 결과·기능 지원 상태. 새로운 분석을 자동 시작하지 않음

한 영역의 데이터가 없어도 다른 영역은 동작한다. “정보 없음”, “아직 분석 안 함”, “연결 실패”, “권한 없음”을 구분한다. 빈 상태에서 임의로 스레드나 인덱스를 생성하지 않는다.

### 상세 화면

- 맥락: 결론, 적용 범위, 출처, 충돌, 현재 revision. ‘이 맥락으로 작업’과 ‘새로 분석’은 별도 동작
- 작업: Hub의 대표 작업·결과 링크와 진행 패널. 내부 보조 작업은 펼쳐 보기
- 정리: 남길 대표 기록, 통합 내용, 아카이브 대상, 보호/제외 이유, 예상 전후 수, 복원
- 이전: 분기점·보존 수준·환경 차이·공유 범위. 미지원이면 이유와 검사 결과만 제공

사용자 화면에 모델이 만든 임의 성공 링크를 사용하지 않는다. 실제 호스트가 제공한 검증된 대상만 열고, 미지원 탐색은 한계로 표시한다.

## 5. 첫 설치와 기존 사용자 전환

### 신규 사용자

1. Workspace 패키지를 설치한다. 이 과정이 별도 플러그인 네 개의 자동 설치라고 가정하지 않는다.
2. 호스트·런타임·component 버전·실행 인증 유무를 진단한다. 비밀 값 자체는 표시하지 않는다.
3. 사용자가 프로젝트를 선택한다. 전체 컴퓨터·전체 대화를 기본 수집하지 않는다.
4. 연결 가능한 현황을 보여준다. 첫 Graph 열기는 기존 initial-open 정책의 범위에서 명시적으로 실행한다.
5. ‘현재 상태 살펴보기’ 또는 ‘작업 시작’ 중 사용자 요청에 맞는 행동을 수행한다.

### 기존 Hub/Graph 사용자

1. 기존 서비스와 데이터 위치·버전을 읽기 전용으로 확인한다.
2. 재사용 가능 / 업그레이드 필요 / 충돌을 보여준다.
3. 호환 서비스에 연결하고 데이터를 복제하지 않는다.
4. 필요하면 별도 승인된 migration과 backup을 진행한다. 활성 Hub 작업은 중단하지 않는다.
5. 기존 단독 플러그인의 비활성화는 사용자가 선택한다. 두 진입점이 남으면 중복 실행 방지 계약이 검증돼야 한다.

지원 OS와 버전은 호환 matrix로 고정한다. 현재 개발 환경이 macOS라는 이유로 모든 OS 지원을 주장하지 않는다. 초기 pilot은 검증된 macOS·Codex 조합을 대상으로 제안한다.

## 6. 요청 해석과 실행 정책

| 사용자 요청 | 동작 | 자동으로 하지 않는 것 |
| --- | --- | --- |
| “이 프로젝트 지금 어디까지 했지?” | 상태·저장된 맥락 조회 | 새 Run·Graph refresh |
| “관련 스레드 찾아줘” | published Graph/허용된 조회 | 무관한 프로젝트 수집 |
| “최신 대화까지 다시 분석해줘” | 명시적 범위로 Graph refresh | 작업 실행·아카이브 |
| “이 결정을 바탕으로 구현해줘” | 적용할 맥락과 범위를 고정해 Hub dispatch | 관련 없는 레포 수정 |
| “끝난 작업 정리해줘” | Fold 계획·검토 카드 작성 | 승인 전 아카이브 |
| “이 계획대로 정리해” | 같은 계획 revision의 유효 승인 확인 후 apply | 변경된 대상에 승인 전용 |
| “이 세션 옮기고 싶어” | Port 지원·범위 검사, preview | 외부 전송·가져온 코드 실행 |

구현 요청은 그 범위의 실행 의사이며 모든 작업에 불필요한 재확인을 추가하지 않는다. 다만 Fold·Port의 부수 효과별 승인은 해당 계약을 유지한다. 읽기 요청인지 작업 실행인지 불명확하면 단 한 번의 구체적인 범위 질문으로 해결한다.

“작업 끝나면 정리안도 보여줘”는 그 작업에 연결된 후속 preview 요청이다. 활성 host workflow 수단이 없다면 끝난 뒤 자동으로 계속할 것을 약속하지 않고 수동 다음 행동을 표시한다. 명시적 자동 아카이브 정책은 첫 버전에 없다.

## 7. 맥락 선택의 품질

Workspace가 모든 대화를 긴 프롬프트로 합치지 않는다. 기존 Graph revision, Fold record revision, 원본 증거 중 작업에 맞는 근거만 선택한다.

- 현재 프로젝트·branch·요청에 적용되는지 확인
- 결정과 추론, 성공 결과와 실패 증거를 구분
- 충돌을 숨기지 않고 필요하면 사용자에게 선택 요청
- Hub가 실행 직전 선택한 근거를 Context Snapshot으로 고정
- 오래된 통합 기록을 발견하면 stale로 표시하고 무단 재분석하지 않음

기록의 화면상 최신 시점과 원본 근거의 관찰 시점은 따로 표시한다. 화면 새로고침은 네트워크/제품 상태의 관찰 갱신이며 semantic 인덱스 재생성과 다르다.

## 8. 작업 흐름 상태

WorkflowTicket 상태 제안: prepared → waiting_user / running → completed / partial / attention / cancelled.

running은 연결된 제품 operation이 진행 중이라는 projection이다. Hub 작업이 끝났어도 요청된 Fold 단계가 승인 대기라면 전체 흐름은 waiting_user다. 사용자가 후속 단계를 취소해도 이미 성공한 작업이 되돌려졌다고 표시하지 않는다.

취소는 ‘아직 시작하지 않은 후속 단계 취소’와 ‘실행 중 Hub 작업 중단 요청’을 분리한다. Workspace 창을 닫는 것은 취소가 아니다. 앱 재시작 시 product operation을 재조회해 연결을 복구하고 기존 요청을 새 Run으로 중복 dispatch하지 않는다.

## 9. MVP와 후속 출시

### M0 — 읽기 전용 연결 검증

프로젝트 선택, capabilities, 현황, 실제 대표 작업 열기, 부분 연결 실패 표시. 새 Run·아카이브·import 없이 기존 서비스 연결과 화면을 검증한다.

### M1 — 초기 pilot: 맥락 → 작업 → 정리

- Graph의 현재 맥락 조회와 명시적 refresh
- Hub의 범위 있는 실행과 대표 링크·진행·결과
- Fold의 동일 완료 Run preview·승인·아카이브·복원
- 단독 플러그인에서 중복 writer 없는 전환
- 재시작·응답 유실·부분 실패 복구

Fold의 원자적 안전성 관문이 미통과면 preview-only pilot으로 명확히 표시한다. Port는 ‘준비 중/호환성 검사’로 남기고 독립 이전 가능 기능으로 표시하지 않는다.

### M2 — 이전 기능

Port의 독립 이력·비공유 데이터 제거·다른 PC/계정 재개·앱 발견 검증 후 기능을 활성화한다. Fold summary를 전달하는 것과 원본 세션 이전을 명확히 구분한다.

### 후속 검토

프로젝트 간 작업 모음, 선택적인 정리 정책 자동화, 팀 환경, 암호화 전달, 장기 보존 정책. 현재 MVP 승인으로 자동 확대하지 않는다.

## 10. 제품 지표와 수용 시험

개인 데이터와 원문을 외부로 보내는 기본 분석 수집은 두지 않는다. pilot 지표는 로컬 집계 또는 사용자가 동의한 실험 기록으로 측정한다.

| 지표 | 정의 / 평가 |
| --- | --- |
| 복귀 후 첫 유효 행동 시간 | 현황을 연 시점부터 올바른 작업/맥락 선택까지; 기존 사용 방식과 비교 |
| 출처 접근 성공률 | 표시한 source 링크를 열어 근거를 확인할 수 있는 비율 |
| 맥락 적용 품질 | 잘못된 branch·오래된 결정 사용 사례를 fixture와 사용자 검토로 측정 |
| 중복 실행 | 동일 사용자 요청 재시도·재연결이 추가 Run을 만드는 횟수; 필수 시나리오 0건 |
| 정리 안전성 | 보호 대상·승인 밖 대상 변경 0건, 복원 검증 |
| 회복 가능성 | 종료·timeout·부분 실패 후 실제 결과와 화면이 재일치하는지 |

합격 조건은 benchmark를 측정하지 않고 임의의 속도 개선 수치로 정하지 않는다. 필수 시나리오: fresh install, existing Hub attach, incompatible daemon, missing Graph, stale context, duplicate dispatch, Fold 승인 후 대상 변경, app restart, unsupported Port, uninstall 동안 활성 작업 유지.

| W4 | 고정 버전 배포 묶음, 설치·전환·제거 E2E | W0~W3 |
| P0 별도 | Port 독립 패키지 실험과 보안 gate | Port 기술 검증 |
| W5 | Port preview/import/export 경험 | P0 및 실환경 E2E |

업무 DAG나 새 daemon을 만들지 않고 gateway/adapter/사용자 흐름에서 구현한다. 실제 registry와 lease의 변경은 기존 제품의 소유 API로만 요청한다.

## 12. 결정 기록과 미결정

확정: 제품명 RUVORA Workspace, Hub·Graph·Fold·Port 독립성, 로컬 우선, 문서 단계.
제안: `ruvora-workspace` 패키지 ID, 한 번 설치하는 모듈 묶음, 프로젝트 중심 첫 화면, macOS pilot, M0→M1→M2 출시.
검증 필요: 호스트 패널·신뢰 승인 수단, component 재사용 handshake, archive 원자성, Port 독립 형식, 초기 지원 버전 matrix.
